FMS deployment architecture

National Fuel Monitoring System (Zambia), shown with four demo stations in three provinces: two in Lusaka, one in Copperbelt and one in Southern.

  • One cloud for every province. All four stations feed the same ingest API and database. The province is a property of the station (stations.province_id), not a separate deployment.
  • Who sees what. The ERB Lusaka officer sees LUS-0001 and LUS-1001, the Copperbelt officer sees COP-0001 and the Southern officer sees SOU-0001. ERB national and ZRA auditors see all four. Owners see only their own company's stations, in any province.
  • Province figures. The ERB provinces page and the analytics national reserve add up stock, sales and days of cover per province from the same data.

How data moves

  • At the station: the PTS-2 controller pushes each sale and tank reading to the edge gateway. The gateway signs the sale with ZRA's VSDC, prints the receipt, and stores everything in a local outbox, so the station keeps selling and fiscalising through internet outages. A keepalived pair can make the gateway highly available.
  • Station to cloud: the gateway syncs batches to /ingest; price and other commands ride back on the replies. Stations without a gateway (direct mode) post jsonPTS to /ingest/pts, and the cloud fiscal-worker signs those sales with ZRA.
  • Users: the web portal, mobile app and partner systems go through the same proxy. core-api serves the owner, ERB, ZRA, admin and partner APIs; analytics serves forecasts.
